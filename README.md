# Sistema de Chamados — Comunicação Interna

> Zé, começa por [José Paulo.md](./José%20Paulo.md) — é mais rápido que entrar
> direto no código.

Sistema de abertura e roteamento automático de chamados da área de Comunicação Interna.
Funcionário abre o chamado sem cadastro; o sistema já roteia pro analista dono (por
público × área × tipo de solicitação), calcula o prazo de SLA em dias úteis, e mantém
um painel + dashboard para os analistas e a coordenação.

Este projeto foi construído **sem acesso direto ao Oracle nem ao Keycloak da empresa**.
Ele roda 100% localmente em modo de desenvolvimento (banco SQLite embutido, login
simulado) para qualquer pessoa poder testar o fluxo completo, e **toda a conexão com
Oracle/Keycloak/e-mail reais fica parametrizada por variável de ambiente** — quem for
subir em produção só precisa preencher o `.env` e rodar as migrations.

## Stack

- **Node.js** (Express) — API + serve o front-end estático de `/public`
- **Banco**: SQLite embutido (`node:sqlite`, modo dev/teste) ou **Oracle** (produção),
  escolhido por `DB_DRIVER`. Os dois drivers implementam exatamente o mesmo contrato de
  repositório (`src/repositories`), então a lógica de negócio nunca muda entre eles.
- **Autenticação**: login local simulado (`AUTH_MODE=dev`) ou **Keycloak** via OpenID
  Connect (`AUTH_MODE=keycloak`)
- **E-mail**: log no console (`MAIL_MODE=console`) ou SMTP real (`MAIL_MODE=smtp`), via
  Nodemailer, processado por um worker em segundo plano (padrão *outbox*: toda
  notificação primeiro vira uma linha na tabela `notificacao`, só depois é enviada)
- **Anexos**: gravados em disco por padrão (`ATTACHMENT_STORAGE=filesystem`), com opção
  de gravar como BLOB dentro do Oracle (`ATTACHMENT_STORAGE=oracle_blob`)

## Requisitos

- Node.js **22.5 ou mais recente** (o modo de desenvolvimento usa `node:sqlite`, módulo
  nativo do Node — não precisa instalar nada além do Node em si). Em produção, com
  `DB_DRIVER=oracle`, essa exigência de versão deixa de ser crítica, mas recomenda-se
  manter Node atualizado de qualquer forma.
- Em produção com Oracle: rede liberada até o banco. O driver `oracledb` roda em **modo
  thin** por padrão (sem precisar instalar o Oracle Instant Client). Só troque pra
  `ORACLE_CLIENT_MODE=thick` se precisar de um recurso que o modo thin não cobre (ver
  [documentação do node-oracledb](https://node-oracledb.readthedocs.io/)).

## Rodando localmente (sem Oracle, sem Keycloak)

```bash
npm install
cp .env.example .env        # já vem com DB_DRIVER=sqlite, AUTH_MODE=dev, MAIL_MODE=console
npm run migrate             # cria data/dev.sqlite3 com o schema
npm run seed                # popula tipos, áreas, analistas e a matriz de roteamento
npm run dev                 # sobe em http://localhost:3000
```

- Página pública de abertura: `http://localhost:3000/`
- Área do analista: `http://localhost:3000/analista/login.html` — em modo dev, a tela
  lista os analistas semeados e loga como qualquer um deles com um clique (sem senha).
- `npm test` roda a suíte automatizada (unitários + API HTTP ponta a ponta) contra um
  SQLite isolado por execução — não precisa do Oracle nem do Keycloak.

## Indo para produção (Oracle + Keycloak)

1. **Banco**: preencha `ORACLE_USER`, `ORACLE_PASSWORD`, `ORACLE_CONNECT_STRING` e mude
   `DB_DRIVER=oracle` no `.env`. Antes de rodar, peça pro DBA revisar
   `src/db/oracle/migrations/001_schema.sql` — é SQL puro e versionado, sem geração
   dinâmica. Depois: `npm run migrate` (agora aplica contra o Oracle) e `npm run seed`
   (ou peça pro DBA revisar/inserir os dados de negócio manualmente a partir do mesmo
   script, se preferirem não rodar direto).
   - As tabelas usam `GENERATED BY DEFAULT AS IDENTITY` (Oracle 12c+). Se a versão da
     empresa for anterior a 12c, troque cada `IDENTITY` por uma `SEQUENCE` + `TRIGGER`
     equivalente antes de rodar a migration.
2. **Login**: mude `AUTH_MODE=keycloak` e preencha o bloco `KEYCLOAK_*` do `.env`
   (`KEYCLOAK_BASE_URL`, `KEYCLOAK_REALM`, `KEYCLOAK_CLIENT_ID`, `KEYCLOAK_CLIENT_SECRET`,
   `KEYCLOAK_REDIRECT_URI`). No Keycloak, criar um client *confidential*, tipo
   Authorization Code + PKCE, com `KEYCLOAK_REDIRECT_URI` cadastrado como redirect URI
   válido. As roles `coordenador`/`analista` (nomes configuráveis via
   `KEYCLOAK_COORDENADOR_ROLE`/`KEYCLOAK_ANALISTA_ROLE`) precisam existir no realm ou no
   client — é delas que o sistema decide quem vê o dashboard e pode reatribuir/editar a
   matriz de roteamento. `KEYCLOAK_ROLE_CLAIM_PATH` (padrão `realm_access.roles`) define
   onde no token ler essas roles — ajuste se o Keycloak da empresa usar outra convenção.
   - Com `AUTH_JIT_PROVISION=true` (padrão), o primeiro login de alguém com role
     `analista`/`coordenador` já cria o registro correspondente automaticamente. Se
     preferir cadastrar manualmente antes, mude pra `false`.
3. **E-mail**: mude `MAIL_MODE=smtp` e preencha o bloco `SMTP_*` com as credenciais reais
   (Exchange/O365 ou o que a empresa usar). Teste primeiro com `MAIL_MODE=console` — as
   notificações continuam sendo geradas e ficam visíveis na tabela `notificacao`, só não
   saem de verdade.
4. **Anexos**: por padrão gravam em `UPLOAD_DIR` (disco local). **Isso fica fora do
   backup do Oracle** — combine uma rotina de backup separada pra essa pasta, ou mude
   `ATTACHMENT_STORAGE=oracle_blob` se a política de TI exigir tudo centralizado no
   banco (mesma tabela `anexo` guarda os metadados nos dois modos; só o conteúdo binário
   muda de lugar).
5. Rode com `npm start` (não `npm run dev`, que fica reiniciando a cada mudança de
   arquivo) atrás de um reverse proxy (IIS, Nginx, etc.) com HTTPS — o cookie de sessão
   só é marcado `secure` quando `NODE_ENV=production`.

## Variáveis de ambiente

Todas estão documentadas com comentário em [`.env.example`](.env.example). Resumo dos
blocos: `APP_*` (sessão), `AUTH_MODE`/`KEYCLOAK_*` (login), `DB_DRIVER`/`SQLITE_FILE`/
`ORACLE_*` (banco), `MAIL_MODE`/`SMTP_*` (e-mail), `ATTACHMENT_STORAGE`/`UPLOAD_DIR`/
`MAX_ANEXO_MB`/`MAX_ANEXOS_POR_CHAMADO`/`ANEXO_TIPOS_PERMITIDOS` (anexos), `SLA_TIMEZONE`.

```

  db/           migrationRunner.js + implementação oracle/ e sqlite/ (pool ou client,

  repositories/ contrato único usado pelo resto do app (nunca SQL direto fora de src/db)
  domain/       roteamento (motor.js), sla (diasUteis.js, slaStatus.js), revisões,
                aprovação — regras de negócio puras, sem depender de banco/HTTP
  auth/         sessão (cookie interno), login dev, login Keycloak, middlewares
  routes/       endpoints Express (público, chamados, anexos, reatribuição, regras de
                roteamento, analistas, dashboard, auth)
  services/     e-mail (outbox + worker), templates de notificação, storage de anexo

  analista/             login, painel (planilha), dashboard de SLA, editor da matriz
  shared/               tokens.css + pequenos helpers JS (fetch, sessão, formatação)

tests/          unitários (domain/) + integração HTTP ponta a ponta (node --test)
```

## Regras de negócio implementadas

- **Roteamento**: primeiro filtro é o público (Holding / Operação-Lojas / Operação-CD /
  Todos). Lojas e CD vão direto pro Rafael Campos, sem passar por área. Holding e Todos
  passam por um segundo filtro de área, mapeada pra Rafael/Daniela/Tiago conforme a
  matriz repassada pela área de Comunicação. Chamados de "Eventos" com público
  Holding/Todos notificam Tiago (dono do SLA) **e** Daniela (co-responsável) ao mesmo
  tempo. Área "Outras" nasce sem dono, numa fila que só a coordenação resolve
  manualmente. Toda essa matriz é editável pela tela **Roteamento**, sem precisar mexer
  em código.
- **SLA**: cada tipo de solicitação tem um prazo em dias úteis (a maioria) ou corridos
  (só Eventos, 60 dias). O prazo só começa a contar quando o briefing é considerado
  completo — se o solicitante indicar um segundo aprovador, o chamado fica
  "aguardando aprovação" e o relógio só começa quando alguém aprovar pelo painel.
- **Revisões**: até 2 de conteúdo e 4 de design por chamado; a partir disso a API recusa
  (`409`) e orienta abrir um novo chamado.
- **Permissões**: só coordenação reatribui chamado, edita a matriz de roteamento e vê o
  dashboard geral de SLA — sempre checado no backend (`requireRole`), nunca só escondido
  no front-end.

## Dashboard de Visitas em Loja (login do Rafael)

Feature separada dos chamados: o Rafael (responsável por Operações/Lojas/CD) faz visitas
periódicas em loja e aplica um checklist em 3 partes (auditoria física, entrevista com
líder, validação com equipe) pelo app "Checklist Fácil". Ele exporta um CSV desse app e
sobe na aba **Visitas em Loja** (só aparece pra quem tem a flag `acesso_dashboard_operacoes`
na tabela `analista` — setada pro Rafael no `seed.js` — ou pra qualquer coordenador).

- **Cada upload substitui o dataset inteiro** do analista (confirmado: o app sempre
  exporta a planilha completa, não incremental) — não precisa e não deve tentar mandar só
  as visitas novas.
- **Formato real do export** (o relatório "Visita Estruturada" do Checklist Fácil,
  confirmado com um arquivo de verdade em 01/10/2026): **uma linha por visita**, com
  **duas linhas de cabeçalho** — a 1ª só marca o pilar (Auditoria física / Entrevista com
  o Líder / Validação com a equipe da Loja) acima do bloco de colunas daquele pilar, a 2ª
  tem o nome de cada pergunta. Como "Percentual da área" se repete uma vez por pilar, o
  parser em `src/domain/visitasLoja/importador.js` trabalha por **índice de coluna**
  (casando cada índice com o pilar da linha 1), não por nome — um objeto `{headers, rows}`
  comum quebraria com nomes de coluna repetidos.
  - `localizarCabecalho` acha a linha que tem "Status" (a linha 2) e assume que a linha
    imediatamente anterior é a de categoria/pilar; se não houver (export sem essa linha),
    cai de volta pra tratar tudo como pilar "outro" sem quebrar.
  - Dentro de cada pilar a maioria das perguntas é Sim/Não; algumas são "de
    acompanhamento" (só preenchidas quando uma pergunta anterior permite, ex. "O que está
    no Mural?"). Não precisamos saber quais são — qualquer resposta que não dá pra
    interpretar como Sim/Não fica de fora do ranking automaticamente.
  - O "Percentual da área" de cada pilar vem pronto do Checklist Fácil (não precisamos
    recalcular a partir das respostas Sim/Não).
  - Nome de CL é normalizado (capitalização de nome próprio) na importação — a planilha
    real tinha o mesmo CL grafado como "Tomas" e "tomas" em visitas diferentes, o que
    duplicava a pessoa no ranking se não normalizasse.
  - Perguntas "de acompanhamento" raramente respondidas (ex. 1 de 6 visitas) são
    estatisticamente pouco confiáveis — `calcularMetricas` só considera uma pergunta pro
    top 5 positivos/ofensores se pelo menos metade das visitas do período respondeu.
- O parser de baixo nível (`src/services/csvParser.js`, função `tokenizarLinhas`)
  reconhece automaticamente delimitador `,` ou `;` (o export real usa `;`), e
  `paraNumero`/`paraData` tratam decimal com vírgula (`57,14%`) ou ponto (`61.54`) e datas
  `dd/mm/aaaa`. Os nomes de coluna são casados por lista de apelidos (`ALIAS_*` no topo do
  arquivo) — se o Checklist Fácil mudar algum nome de coluna, é só ajustar essas listas.
  A resposta de `POST /api/visitas-loja/importar` retorna `avisos` quando loja/CL/
  resultado geral não foram reconhecidos.
- O dashboard (`public/analista/operacoes.html`) tem: cards de visão geral (total de
  visitas, lojas, CLs avaliados, média geral, melhor/pior loja), donut de distribuição
  Sim×Não, os 3 pilares com clique pra detalhar (drill-down de todas as perguntas daquele
  pilar, não só o top 5), top 5 positivos/ofensores, ranking de lojas e de CLs por média, e
  um card de "foco principal" gerado a partir dos piores indicadores. Clicar em qualquer
  pergunta (no drill-down do pilar ou nos top 5) expande a lista de **quais lojas
  responderam Sim e quais responderam Não** pra aquela pergunta especificamente.
- **Perguntas faseadas** (migration `003_pergunta_derivada.sql`): o Checklist Fácil libera
  uma pergunta seguinte (texto livre/categórica) só quando a anterior é respondida "Sim" —
  ex. "A Loja possui a comunicação do Programa Vida Plena e Canal de Ética?" (Sim/Não)
  libera "Informe se a Loja possui as duas comunicações, uma ou nenhuma." (As duas
  comunicações / Somente Programa Vida Plena / Somente Canal de Ética). O importador
  detecta isso por **correlação**, não por nome de coluna: se toda vez que a coluna N está
  preenchida a coluna N-1 (do mesmo pilar) foi "Sim", e a maioria das respostas de N não é
  Sim/Não, N é tratada como derivada de N-1 (campo `indicador_pai` em
  `visita_loja_indicador`). Isso foi necessário porque a planilha real tem linhas com erro
  de preenchimento (uma pergunta de texto livre respondida como "Não" por engano) que
  quebrariam uma regra mais simples tipo "nunca é Sim/Não". No dashboard, clicar na
  pergunta-mãe mostra também a quebra de respostas da derivada (`respostasSecundarias`:
  % e lojas por opção de resposta) — a derivada não aparece mais como pergunta
  independente na lista do pilar.

## Limitações conhecidas / próximos passos

- Cálculo de dias úteis trabalha em UTC (ver comentário em `src/domain/sla/diasUteis.js`)
  — perto da virada do dia pode variar em relação ao fuso configurado em
  `SLA_TIMEZONE`. Refinar com uma lib de fuso horário se isso importar na prática.
  Feriados nacionais/locais ainda não entram no cálculo (tabela `feriado` existe no
  schema, só falta popular e conectar).
- Upload de anexo na abertura pública não exige login (é o próprio fluxo sem cadastro) —
  há uma validação de quantidade/tamanho/tipo, mas nenhum token de uso único; considerar
  isso como hardening futuro se o volume de abuso for uma preocupação real.
- Aprovação do segundo aprovador hoje é feita por um analista logado clicando "Aprovar
  briefing" no painel (representando que a aprovação chegou por fora — e-mail, verbal).
  Um link de aprovação assinado, mandado direto pro e-mail do aprovador externo, é uma
  evolução natural se isso virar fricção no dia a dia.
- Templates de e-mail são texto simples (sem HTML) — trocar por algo mais elaborado é
  só mexer em `src/services/notificacaoTemplates.js`.
- Sem testes end-to-end de UI (Playwright/Cypress); a cobertura automatizada hoje é
  unitária (regras de negócio) + integração HTTP da API (`npm test`).
